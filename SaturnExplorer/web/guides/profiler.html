How the profiler works, and how we know its numbers are right

Saturn Explorer's profiler shows where a running Sega Saturn game spends each frame: which processor is busy, what crosses the buses, how full memory is, and which functions cost the most. This page explains how it gets those numbers and what was done to check them.

Looking for what a particular bar, column or message in the panel means? See the Profiler panel reference.

What it shows

Frame time
For each of the two SH-2 processors: time busy, stalled waiting on the bus, asleep, or switched off. Also VDP1 drawing work, the SCU DSP and the 68000 sound processor.
Bus traffic
How many requests each device received (work RAM, VDP1, VDP2, sound, CD, cartridge), and how many bytes each DMA level moved and between which buses.
Memory
For each fixed RAM area, how much holds data and what is being rewritten.
Functions (optional)
The game's functions ranked by the processor time each one uses per frame.

How it works

The profiler lives in two places: a patched copy of the Mednafen emulator, which does the counting, and Saturn Explorer, which displays it. They talk over a local connection.

EmulatorCountSmall counters are added at the exact points where work happens: a bus request, a DMA start, a VDP1 command, a processor going to sleep.
EmulatorClose the frameAt the end of every frame the counters are packed into one numbered record and reset to zero.
ConnectionSendEach record is delivered once. If any are lost, the gap is counted and reported instead of hidden.
Saturn ExplorerShowThe panel keeps a history of frames and draws shares, tables and a strip you can scrub through.

Counters are always on and cheap

Each counter is one addition placed on a code path that already does far more work, so counting costs almost nothing. The patch only inserts code; removing it restores every emulator file byte for byte.

Function timing is opt-in and costs speed

To know which function is running, the profiler has to look at every instruction both processors execute. It follows calls and returns to keep track of the current function, and charges the cycles since the previous instruction to it. Time spent asleep or stalled is not charged to any function.

When the profiler cannot be sure which function owns some code (for example code that was already running when profiling began, or an interrupt handler), it files that time under the raw address instead of guessing. Time it could not assign at all appears in separate rows labelled Other and Not observed.

Scrubbing back

While you are live the panel shows the newest frame and averages the frames ending at it. When you scrub the emulator's recorded history back to an earlier frame, the Frame, Buses and Functions tabs show that frame instead, and an averaging window is the frames ending at it. A line under the controls says which frame is shown and which is newest, and the history strips mark it with a red line. The frame is matched by its identity (timeline and frame number), so after a rewind the replayed frames are never confused with the ones they replaced.

A rewind (Play From Here) or a state load starts a new history, and the profiler keeps the two apart. An average stops at the rewind instead of mixing in frames from before it, and when that makes the window shorter than the span you picked, the line under the controls says so, for example "Averaging 78 of 600 frames (the rest are from before a rewind or state load)". The history strips break at the rewind and draw a faint divider there. If you scrub to a frame from before a rewind, the strips end at the red mark: the frames that followed it in that history were replaced, so they are not drawn after it.

If the profiler has no record of that frame (it was off then, the frame is older than the last 3600 the panel keeps, or the emulator does not report frame identity), the Frame, Buses and Functions tabs read "No Profiling Data" and the line under the controls gives the reason. The panel never falls back to the newest frame. The same holds after Clear while scrubbed. The Memory tab keeps showing the bytes of the displayed frame, as before.

It says when it does not know

Every record carries flags for which measurements it actually contains. The panel shows "not available" or "1 of 4 frames" where a value was not measured, and never treats a missing measurement as zero.

How it was verified

The checks run from small to large. Each one covers something the one before it cannot.

Tests that run the real emulator code

The component tests compile the actual patched Mednafen source files, with only the surrounding devices replaced by stand-ins. Expected values are derived by hand first. For example, a cache miss must count as exactly 4 bus requests, a cache hit as 0, and a write as 1.

Tests that prove the tests can fail

A test that always passes proves nothing. So the suite also breaks the code on purpose, one small change at a time, and requires a test to fail each time. More than 50 such deliberate breaks are checked across the counting code, the call tracking and the emulator hooks, and every one is caught.

A purpose-built Saturn program with known answers

The main proof is a small Saturn program, called V1, written for this purpose. It runs through 14 phases. Each phase does one known thing, so the numbers the profiler should report can be worked out in advance. Those expected values were written down before the program was run.

PhaseWhat the program doesWhat the profiler must report
IdleSleeps all frameA baseline: nearly the whole frame asleep
BusyRuns a loop of fixed lengthBusy time matching the loop's cycle count
FunctionsCalls two functions of known length12,003 and 4,003 cycles
BusA fixed number of reads and writes per deviceThe same counts, device by device
VDP1Draws one command, then manyCommand counts and drawing work
DMATransfers of known size, alone and during a drawTransfer counts, bytes, and processor stall time
Second CPUSwitches the slave SH-2 on, then offThe exact time it was powered within the frame
Sound CPURuns, idles and stops the 68000Executed versus idle cycles

Run on a real Saturn BIOS in the patched emulator, all 48 checklist rows matched, in both of the emulator's cache modes. Switching individual counters off made the matching rows fail, which shows the checklist can tell a working profiler from a broken one.

Checking that measuring does not change the result

The same program was recorded with function timing off and on. Every counter other than the function table is identical in both recordings. An earlier build did not pass this check: turning function timing on shifted two figures slightly. That was traced to the emulator updating every device before each instruction, and fixed.

Working alongside the debugger

Breakpoints, single-stepping and tracepoints were exercised with the profiler running, including Mednafen's own built-in debugger. One real bug was found this way: after stepping in the built-in debugger, the function table froze on one function. It now recovers on the next frame, and a frame the profiler could not observe fully is left out of the function table instead of showing a wrong split (the Frame tab counts it in "Function attribution: on in k of n frames").

Measuring the cost on a real game

A separate benchmark on an idle machine measured overall speed with the frame limiter off, five runs of each setup, on the same scene:

SetupSpeedExtra time per frame
Profiler not connected116 fpsbaseline
Connected, function timing off101 fps+15%
Connected, function timing on38 fps+206%

The Saturn runs at 60 fps, so a game that reaches these speeds stays at full speed with the counters on, and drops below it with function timing on. One of the five baseline runs was about 6% slower than the rest, so the +15% figure carries a range of roughly +8.5% to +16%.

Everything else

  • The full automated suite of 140 tests passes on the current code.
  • A race detector was run over the connection code. It found one real race in how listening sockets were closed, which was fixed.
  • Each change was reviewed independently, and several review findings were reproduced and fixed before merging.

What has not been verified

Read the numbers with these limits in mind

  • Real games are checked less than the test program. V1 proves the counters on known inputs. On a commercial game the numbers are plausible and consistent, but there is no independent answer key.
  • It measures the emulator, not the console. The figures are faithful to what Mednafen emulates. They were not compared with real Saturn hardware.
  • "Busy" includes slow bus waits. Only sleep and DMA stalls are separated out.
  • Function time is self time. Time in a function's callees is charged to the callees.
  • A breakpoint left set in Mednafen's own debugger pauses function timing until it is cleared. Those frames are left out of the function table.
  • The panel was checked by hand once, on the test program: every tab showed the expected values, and breakpoints and stepping worked alongside it. Its automated tests run without a display.
