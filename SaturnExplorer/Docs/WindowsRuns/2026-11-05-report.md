**A9-20, two instances in one folder.** Instance 1 imported `alpha`+`beta`; instance 2 (same folder) imported
`gamma`; instance 1 then imported `delta`; instance 2 imported `epsilon` and, later, `zeta`. Both closed. Final
`saturn_functions.txt`:

```
06001000 alpha_func
06002000 beta_func
06003000 gamma_func

```

All six survive; neither instance overwrote the other. Caveat: the saves were sequential, not truly simultaneous.

**The `.lock` file.** `saturn_functions.txt.lock` (0 bytes) stays beside the data file after exit. No sharing
violation: `FileLock` opens it with `FILE_SHARE_READ|WRITE|DELETE` and takes `LockFileEx`. I then held the lock
from a separate process for 12 s and saved from instance 2: instance 2's UI thread blocked, `Process.Responding`
was **False** at 4 s, and the save completed after the lock was released (zeta written, instance responsive
again). So a second instance that saves while another holds the lock **freezes its window until the lock is
released**, with no timeout (`FileLock(path, wait=true)` in `FileWrite.cpp:379`). With a real second instance the
lock is held for one write, so it is short; a crashed or stuck holder of the OS lock is released by the OS when its
process dies. I rate this a design note, not a defect.

## Defects found

None of these are in the tasks' pass/fail claims; they are what I would look at.

1. **`FrontEnd.vcxproj` and the other projects pin v142 (VS2019).** `RomHackingTools.sln` does not build on a
   machine that only has VS2022. Suggested: `v143`, or leave it unset so the IDE picks one. Repo/environment.
2. **`FrontEnd.vcxproj` still lacks `SE_NATIVE_MENUBAR`** (follow-up item 1, second bullet). Repo bug.
3. **A second instance's UI thread blocks on the data-file lock with no timeout** (`FileLock(..., wait=true)`
   from `SaveStore`). Window shows "Not Responding" for as long as another process holds the lock. Design note.
4. **`mednafen-se` is not found under a path with characters outside the ANSI code page** (known). The `é` case
   works but the field prints `?`, which is the font subset.
5. **CMake registers no fault-injection or loader-fuzz test on Windows.** By design (fork, glibc), so Windows has
   no coverage for A6 and A9's fuzz harness.
6. **`SOURCE.txt` rebuild recipe omits Windows-only configure flags.** It gives `CPPFLAGS="-DSE_MDFN_REWIND=1"`; the
   recorded configure on this machine used `-DUNICODE=1 -D_UNICODE=1 -DSE_MDFN_REWIND=1`. `SOURCE.txt` says
   `install.py` adds toolchain flags, so this may be intended; worth one sentence in the file.

## Things that surprised you

- **ImGui widgets and synthetic mouse input.** The Win32 process I used for automation is DPI-unaware, the screen is
  at 125 %, and `CopyFromScreen` captures physical pixels while `SetCursorPos` takes logical ones. I first clicked
  at the wrong spot for an hour (a click meant for "Windows" opened "Demo"). Mapping that worked: logical =
  (image pixel + window left) / 1.25. ImGui also needs the cursor to rest on a widget for a frame before the press,
  otherwise the click is ignored.
- **A window launched behind other windows shows a white client area** until it is brought to the foreground
  (`SetForegroundWindow` plus an Alt tap), after which it draws normally. I believe this is occlusion handling in
  the D3D swap chain, not a bug, but did not dig.
- Deleting or moving `settings.ini` while a just-closed SE is still shutting down is racy: the exiting process
  rewrites it. Wait for the process to end first.
- The first-run notice uses `mLauncher.UsesBundledMednafen()`; with a recorded `[emulators] mednafen` (as on this
  machine) it never appears, so the check needs fresh settings.
