# SH-2 Pseudocode (decompiler) guide

The **SH-2 Pseudocode** panel turns the SH-2 function you are looking at into C-like pseudocode.
It runs Ghidra's decompiler engine in-process, against a snapshot of the machine you are looking
at: a savestate, a paused or running emulator, or a recorded frame. Nothing is sent anywhere,
and no Java or Ghidra install is needed.

Design and rationale: `Docs/Decompiler/DESIGN.md`. Build plan and what was built: `Docs/Decompiler/PLAN.md`.

## Opening it

**Windows → Debugger → SH-2 Pseudocode**. By default it docks beside SH-2 Assembly. To pick a function, use any of these:

| From | How |
|---|---|
| The panel | Turn on **Follow PC**: it shows the function the chosen CPU is in. Or type an entry address (hex, any mirror, e.g. `06004000`) and press Enter. A mirror is decompiled as code running there: `26004000` runs the same bytes through the cache-through area, so a `mova` there yields a `0x26…` pointer. The function keeps its canonical name. Enter always asks: after **Stop**, or after a failure, typing the same entry again and pressing Enter decompiles it, where without Enter the panel does not ask the same question again by itself. |
| SH-2 Assembly | Right-click a line → **Decompile Here**. |
| Call Stack | Right-click a frame → **Decompile**. |
| Registers | In the **SH-2** tab, right-click the **PC value** (not its label) → **Decompile**. |

The combo picks **Master SH-2** or **Slave SH-2**. That only decides whose PC Follow PC reads. With Follow PC on, switching follows the other CPU. With it off, the output stays, because both CPUs share RAM.

## Reading the output

- The status line shows the source and frame, and the function's name and entry. It also shows the panel's state: decompiling, stale, unsupported, or out of time.
- **Click a line** to jump SH-2 Assembly to the first instruction it came from. "First" means the lowest address: a statement is built from every instruction whose result it combines, so a line is often several instructions (about four lines in ten of those that have any are), not always next to each other, and a line can hold code from below the function's entry (a shared epilogue). A line with no instruction behind it (a declaration, a brace) does nothing when clicked and has no tooltip.
- **Hover a line** to see where it came from. The tooltip says, for example, "Decompiled from the SH-2 instruction at 0x06086F54 (an address in the program, not a value in this line). Click to show it in SH-2 Assembly." The number is the address of the SH-2 instruction, as SH-2 Assembly shows it; it is not a variable, a parameter or a value in the line, whatever the line holds. When the line is built from several instructions the tooltip says how many and lists their addresses (the first eight, then a count), for example "Decompiled from 3 SH-2 instructions" and `0x06086F54, 0x06086F58, 0x06086F60`; the click shows the first, and **Show Other Instructions** in the right-click menu shows each of the others. Not every instruction has an address on a line: an operation folded into the expression that uses it (a move, an addition, a literal load) has none, and an instruction in a delay slot is carried by its branch, so its line is the branch's and the instruction is the row after the branch in SH-2 Assembly. There is no way back yet from an SH-2 Assembly row to the line that came from it.
- **Right-click a line** for these:
  - **Show in SH-2 Assembly**, and, for a line from several instructions, **Show Other Instructions**.
  - **Rename Function...** and **Rename Callee 0x...**: names go into the same store Call Stack uses. Call Stack shows a name only on frames whose function it has identified, not on "Func unknown" frames. SH-2 Assembly has no label column, so a name does not show on its rows.
  - **Set Function Start Here**: use it when the finder guessed the entry wrong.
  - **View in Memory**.
  - **Copy Line** and **Copy Function**.
- **Hardware registers** have names, such as `VDP2_TVMD`, `SCU_D0R` and `SH2_DVDNT`. There are 335: VDP1, VDP2, SCU, SMPC, SCSP, the CD block, `MINIT`/`SINIT` and the SH-2's own peripherals. Bus registers are named at their cached and cache-through addresses. Every access to a register area stays in the output in the order the code makes it: a write before a poll, the poll itself, a write the next one replaces, and a read whose value is unused. A read whose value is unused is also kept when its address is computed and never becomes a constant, since it may be a register. A read of ordinary memory whose address does become a constant is dropped as usual. Each access keeps the width the instruction uses (a word store through a byte pointer stays one word store), and a value read once is printed once, stored in a variable when it is used more than once.
- **Hardware explanations** appear as a trailing `// …` comment on the line. They say what the name alone does not:
  - a documented register pair accessed whole, such as a 32-bit VDP2 scroll write;
  - which watchdog register a keyed write selects;
  - a register reached through a mirror, which the output shows by address;
  - what a register returns when its reads and writes reach different fields, such as `SCU_IST` or `CD_CR1`, if the function also writes it.
  - a write whose effect depends on its value: `SH2_CCR` with CP (bit 4) set purges the whole cache, `VDP1_PTMR` with bit 0 set starts drawing and with bit 1 set arms drawing at each frame change; a write to `SMPC_SF` sets it to 1 whatever is written;
  - an access through `0x4xxxxxxx` or `0xAxxxxxxx`, which is an associative purge of a cache line and not a memory access (the slave SH-2's idle loop does it); the purge invalidates the whole 16-byte line of the word it names, so every other word of that line the function reads is kept as a read too.
- **Volatile memory.** Sound RAM, shared with the 68000, is always treated like a register. For other memory another processor changes, such as a mailbox shared with the slave SH-2, click **Volatile** in the toolbar and list the ranges, for example `0x26001000-0x26001003, 0x06002000`. Every access there is then kept, through every address that reaches it: both partitions, the bus repeats and the 1 MiB mirrors of high work RAM (0x06000000-0x07FFFFFF) and low work RAM (0x00200000-0x003FFFFF). Each range is widened to whole longwords, so a word access touching one marked byte is kept too. A literal-pool word in a marked range is read, not folded from the snapshot, and a jump table in one is not recovered into a fixed `switch`: the jump stays indirect, with a warning. Hardware areas are treated the same way. Changing the list marks the output stale, and signatures learned under the old list are no longer lent. The list is saved in `settings.ini` under `[decompiler] volatile`. A word the function itself names under two addresses (a mailbox stored through `0x26003304`, purged at `0x46003304` and polled at `0x06003304`; a colour RAM entry at `0x25F00000` and `0x25F01000`) needs no mark: it is kept as if marked, in that function, because the data flow would otherwise forward a store past a write to the other name (work RAM through its partitions, bits 28-27 and its 1 MiB repeats; VDP2 VRAM every 512 KiB, colour RAM every 4 KiB and, in colour RAM mode 0, 0x800 bytes on; the VDP1 frame buffer every 256 KiB; the extended RAM cartridge, 0x02400000-0x027FFFFF, every 512 KiB inside each 2 MiB half, as a 1 MiB cartridge decodes it; the cache's data array, 0x80000000 and 0xC0000000, 4 KiB). A purge written through 0xA6003304 is the same purge as through 0x46003304, and it names the 16-byte line 0x06003300-0x0600330F: a poll of 0x06003308 in the same function is kept too. A function that writes `VDP1_TVMR`, `VDP2_RAMCTL` or `VDP1_FBCR` re-addresses the frame buffer or colour RAM from then on (a frame change makes the same address the other buffer), so every access it makes to that memory is kept as if marked; a frame change the function does not write (the automatic one) is not seen, and a frame buffer the function reads back after waiting for the frame end needs its range marked. Without a mark, a poll of shared work RAM through one address only can print as `do {} while (true);`, and the engine then removes everything after the poll as unreachable. When that removes a hardware access, or any access through a pointer, the output says so: an amber line on the missing access's instruction, and a warning, name the register (or say the access is through a pointer) and the cause -- a poll that never ends as analysed, or a test always decided the same way -- and the signature is withheld. If that check cannot run to the end (an engine error, a stop, the time budget), the warning says the removed code was not checked and the signature is withheld all the same.
- **Calls into a function already decompiled** this session use its recovered signature: argument count, types and return. A signature is used only when its recovery was complete. That means no bad instruction or unresolved jump, no jump table recovered only in part, an analysis that settled, every function it calls already has a known signature (and it does not call itself), every argument it reads is in the signature, and every return goes back to the caller. So decompile callees first: a caller shown before its callees is decompiled again, with their signatures, the next time it is shown. A function that calls into the BIOS without an image, or through a computed pointer, never lends its signature. A signature is lent with what the analysis proved the function leaves alone: a register (r2-r7, SR, MACH, MACL) it was shown to keep at every return is read after a call to it as the caller's own value, not as a new unknown one (`extraout_r4`), so a caller that passes a parameter through such a helper keeps the parameter and its own signature. A register the function changes on any path, or that was not proved, stays unknown after the call. That includes the registers the calling convention keeps for every callee: a lent function proved to change r8-r14, GBR or VBR leaves the caller reading its value as `extraout_r13` (and withholds the caller's signature on it), and one that leaves r15 a constant distance above where it found it (it pops words its caller pushed) is taken to have done so, so the caller's later stack reads land on the right words. One that leaves r15 below where it found it (`rts ; mov.l r5,@-r15`, a value handed to its caller on the stack) is withheld, and so is its caller: a signature has registers only. A function that reads a register no signature can pass is not lent a signature at all, and nor is any caller of it: r0-r3, r8-r14, GBR, MACH, MACL, or the T flag (`movt`, a branch, `addc`) read before it is written, or a return in r0 made only of such a register (`rts ; sts macl,r0`, which the engine prints as returning nothing), or a return the engine prints as returning nothing whose value in r0 depends, by data or by which path the code took, on an input the signature does not hold: r0's entry value read by an operation or a test, the T flag the caller left, SR, r1-r3, r8-r14, GBR, MACH, MACL, a parameter in r4-r7 that the signature drops, or a stack argument (`stc sr,r0 ; cmp/pz r4 ; bt L ; or #0xF0,r0 ; L:`, `tst r4,r4 ; bt L ; add #1,r0 ; L:`, `tst r3,r3 ; bt L ; mov #1,r0 ; ... ; L: mov #2,r0`, `bt L` on the caller's T; two values are two when two instructions made them, even if both are loads or both are `r4` plus a constant). A path that leaves r0 alone is no read of it, and a choice made by a constant or by a parameter the signature holds loses nothing a caller can see, so those still lend, whether or not the function calls: `bsr g ; ... ; rts ; mov r8,r0` returns the caller's r8 across a call that keeps it, and is withheld like the leaf (a value a call returned is not taken for such a register). So is a value the function put in r0 before a call to a function that keeps r0 (`mov r4,r0 ; bsr g ; nop ; rts`, where g is `rts ; nop`): the engine kills r0 at every call, prints no return, and the code returns r4. Compiled code that leaves a scratch value in r0 across such a call is withheld too (10 of the 610 signatures lent for one game image, 22 of 1,006 for the other, before the rule); the callee's address in `jsr @r0` is not counted. The status register read whole and returned or stored as it is, where the engine keeps that value (the compiler's `stc sr,r1 ; mov.l r1,@r14 ; mov.l @r14,r0`, an interrupt-mask helper), is machine state and still lends; SR stored through a pointer the function was given (`stc sr,r1 ; mov.l r1,@r4`) is an input, because the caller reads the word back after the call, and withholds; the bare `rts ; stc sr,r0` is printed as returning nothing and is withheld like `sts macl,r0`. A write to SR, GBR or VBR (`ldc`) stays in the text as `Write_SR(...)`, `Write_GBR(...)`, `Write_VBR(...)`, and with it the read of the register it was loaded from; a control register whose entry value only goes back into a write of the same register (GBR saved and restored round a call, the interrupt mask raised and put back with the other SR bits kept) is machine state and still lends, one whose value is branched on, compared, used as an address, or returned or stored as a field of it (`and #1`) is an input and withholds. Text for a caller of a function that has no signature is the engine's convention, where r8-r14 and GBR survive a call: a register set up for such a function before the call does not show. **A structure returned by value:** the SH ABI of both compilers passes its address in r2, which the engine's convention has no input for. When r2 holds the address of a local at a call whose function has no lent signature, the local and everything above it in the frame is treated as memory the call may write (an array, `axStack_c [2]`, or locals whose read after the call is not folded to the value stored before). A frame address with a constant added counts from the address it was made to; one with a register index added or subtracted (the address of an array element, `a[i] = f()`, or `p - i`), or one a loop keeps moving, counts from the frame's lowest local, since the index may be negative. The call itself still shows no argument for r2, and only r2 is looked at: a frame address in r0, r1, r3 or r8-r14 (the frame pointer, or a scratch left over) is not taken for a pointer the call uses (r3 holds one at dozens of call sites of compiled code, as scratch). The same note is said for a frame address in r7 with r4-r6 untouched, and in a stack argument word the engine drops from the call: every one when r4-r6 or r5-r7 are untouched, otherwise every word from the first one the code did not write on every path up. And when, after a call to a function with no lent signature, the code reads back a word it wrote at or above the stack pointer that the callee itself writes through its own stack pointer (a hand-written callee that hands a value back in its stack argument slot), that word is not taken for the value stored before the call, and a note at the call says why. One more limit, of hand-written code: a caller that sets the T flag, calls a function lent as returning the status register whole and uses the result is lent without the registers the compare read. An absolute address is taken never to be in the stack, as the engine takes it: a callee that overwrites its own saved register through a constant address that happens to be its stack slot is still shown as keeping it.
- **Comments** you add in SH-2 Assembly (right-click → **Edit Comment**) appear as a trailing `// note` on the first line decompiled from that instruction. Editing one never re-runs the decompiler.
- **At a halt on `jsr @rN`, `jmp @rN`, `braf` or `bsrf`**, the call's line and the status line show where the call goes this time, for example `r2 = 0x06031510 at the halt`. The target is computed, so another call may go elsewhere.

## The BIOS

Calls into the BIOS stop at the BIOS boundary unless you give the panel an image. Click the **BIOS** button in the panel's toolbar → **Choose BIOS Image...** and pick your own dump; it is never shipped, and it must be 512 KiB or smaller. The image is mapped at `0x00000000`, so BIOS functions decompile and are named `bios_0x…` until you rename them. The path is saved in `settings.ini` under `[decompiler]`.

## When the output is stale or missing

The output is always for a specific snapshot. If what you are looking at changes, the output is marked rather than silently replaced. Examples of a change: a Hex Editor write, a scrub, the emulator running on, a rename, or a new BIOS image.

| You see | Meaning | What to do |
|---|---|---|
| **stale: frame N** | The emulator has moved on since this was decompiled. | **Refresh**, or turn on **Auto-refresh**. Auto-refresh only works with Follow PC on, refreshes at most every 30 frames, only once the PC has left the function shown, and is off by default. A function shown as *too large* has no body to be inside of, so it counts as left once Follow PC no longer resolves the PC to its entry: while the game stays in it, it is not run again every interval. |
| **stale** (no frame number) | The output is for earlier inputs than the ones on screen: a rename, a function start, the volatile list, a write, a scrub, a BIOS image. Output that matches the inputs is never stale, not even while **Refresh** or a re-ask is running: "decompiling…" says that, and the output keeps its brightness and its register hint. The tooltip says which of these it is. *Its replacement is shown when it is ready*: the new question was sent and "decompiling…" is up. *You stopped its replacement*: **Stop** was pressed; **Enter** in the entry box or **Refresh** asks again. *Decompiling is disabled for this session*: nothing can be asked; see the red line below. Otherwise nothing is being asked, and the tooltip names why: a running emulator that has moved on (**Refresh**); Follow PC with the PC in memory no function is found in (step or run the emulator and **Refresh**, or turn Follow PC off); Follow PC with no registers to read (turn it off and type an entry, or **Refresh** once it has them); **Decompile** on an address no function was found for (ask about another address, or type an entry); or an entry the box refused or cannot take, which stays the question until you correct it and press **Enter**. | Wait, press **Enter** or **Refresh**, or restart, as the tooltip says. |
| **PC-relative load in a delay slot at 0x… that other code also jumps to: not trustworthy** (amber, greyed) | A `mov.l @(disp,PC)` or `mova` sits in the delay slot of a delayed branch, and something else jumps straight to that slot. The slot reads relative to the branch's target when the branch is taken (every delayed branch is modelled that way) and relative to its own address when entered by the jump, and the output can show one. | Read the assembly for that slot. The rest of the output is shown for orientation only. |
| **Flows into … at 0x… ; the function is cut off there** (amber; "and at N more places" when there are several) | Flow reached memory that is not captured: the BIOS with no image, or an unmapped area. That path stops there. A path into memory that is not captured which the analysis proved can never be taken (a switch on a constant its own bound check excludes) is mentioned as followed and removed, and is not a cut: the function is not marked truncated for it. | Give the panel a BIOS image. If the code should not go there, the entry is probably wrong: **Set Function Start Here**. |
| **Flow runs into bytes that do not decode at 0x…** (amber) | Flow reached data in captured memory: a literal pool, a jump table, or code read from the wrong place. That path stops there. Four or more such places are flagged as "the entry is probably not code". At an odd address (a jump table entry or a pointer that is no code address: an SH-2 instruction starts at an even address) the warning says so, flow stops there as it does at bad bytes, and the case shows `halt_baddata();`; nothing is decoded from the middle of the instruction before it. An entry typed at an odd address is refused ("an SH-2 instruction starts at an even address"). | Check the entry in SH-2 Assembly; **Set Function Start Here** if it is wrong. |
| **0x…: Treating indirect jump as call** (or **as return**, **Could not recover jumptable**) (amber) | The engine could not resolve a `braf`/`jmp @rN` switch. Its cases are missing from the output, which shows one indirect call instead. | Read the cases in SH-2 Assembly. |
| **0x…: Sanity check requires truncation of jumptable: cases may be missing** (or **Second-stage recovery error: …**) (amber) | The engine recovered a switch only in part. The cases it dropped are missing from the output, and the function lends no signature. A note about case labels ("may not be properly labeled", "Bad switch case") means every case is there but its label may be wrong. | Read the table in SH-2 Assembly. |
| **0x…: jmp is taken for a tail call to 0x…** (amber) | The engine read an indirect jump with one possible target as a tail call, and assumes a return after it. The code at the target is a function of its own, not part of this one's body and not shown here, also when nothing else reaches it (a `braf` or `jmp` over data words to code that returns on its own is the same). When the target is not captured, the panel says so too. | Check the target; to see what runs there, set a function start at the target and decompile that; give the panel a BIOS image if the target is in it. |
| **0x…: flow runs into NAME at 0x…, another function's entry** (amber) | A tail branch, a fall-through or shared code reaches a known function's entry. That function's code is shown as part of this one. One line for each such entry: when that function in turn jumps into a third, both are named. An entry counts even if its first instruction is dead code the output leaves out (a stack frame it never uses), and a function the panel has lent a signature to counts as one whether or not the function finder listed it. | Expected for a tail call. Otherwise check both entries. |
| **0x… is not reached from this entry** (amber) | The function found for an address (the PC, or the one you asked about) never gets there. The finder picked the wrong entry. | **Set Function Start Here** on the real entry. |
| **Entry: …** (amber) | The finder is unsure of the entry, and says why: an `rts` that may end the function, a branch before that `rts` that jumps past it (an early return), a jump table of unknown length, or code that never reaches the address. The confidence shown beside the source drops by 20. An entry found only by the `rts` scan always shows "guessed from the previous rts". | Check the entry; correct it if needed. |
| **0x…: reads REG, which is write-only** / **writes REG, which is read-only** (amber) | The code reads back a register the hardware does not return, or writes one that ignores writes. The output shows the access as written. For the SMPC's write-only registers the read returns the last byte written to the SMPC, to any register (its bus buffer); a read of `SMPC_SF` not masked to bit 0, and of the port data registers not masked to bits 6-0, gets that byte in the other bits (note). | Expected in some code. The value read is not the value written. |
| **0x…: one 4-byte write covers REG1 and REG2** (amber) | One access spans two 16-bit registers of the VDP, SCSP or UBC that the manuals do not document as a pair; the bus makes it two 16-bit accesses, the first register taking bits 31-16 and the second bits 15-0. The output names only the first, with a `_` prefix. Documented pairs, such as the VDP2 scroll values, are explained on the line instead. A long over one 16-bit register and a word the map does not name (`VDP2_PRIR`, `VDP2_RAMCTL`, `VDP1_ENDR`, `SCSP_DMEAL`) gets its own caution saying which half the register takes and where the other goes. | Check what the code meant to write. |
| **0x…: a 1-byte write to REG writes the whole 16-bit register** / **a 2-byte write to REG, a 32-bit register, …** / **a 1-byte read of REG, a 32-bit register, is an address error** / **a 4-byte write to REG, a 16-bit register, is an address error** / **a 2-byte write to REG, an 8-bit register, reaches only it** / **a 1-byte write to SCU_PPD writes the whole 32-bit register** (amber) | The access has a width the register does not, and the hardware does not just take the bytes the code carries (Mednafen is the reference; every register, width and direction is in `FrontEnd/tests/HardwareWidthTable.golden.txt`, generated from the rules in `SaturnHardwareMap.cpp`). A byte write to a VDP1 or VDP2 register writes all 16 bits, the other byte being whatever was last on the data bus; the SCU's DSP ports (`SCU_PPAF`, `PPD`, `PDA`, `PDD`) are not masked either, so a byte or word write writes the whole 32 bits; a word write to a 32-bit on-chip register (divider, DMAC) takes the register whole at its own address (a write to the dividend starts a division) and does nothing at +2; a word read returns the low half at +0, and at +2 too for the divider and the bus state controller but not for the DMAC, where it returns 0 and reads nothing (no flag is armed); a byte access to one is an address error, and Mednafen then makes it: a byte write stores the byte in both bytes of the register's low half (and starts the division at `SH2_DVDNT`), a byte read returns bits 15-8 of the register whichever byte was asked for; a long access to an on-chip register below `0xFFFFFF00` (the FRT, the INTC, the DMAC's DRCRs, `SBYCR`, `CCR`) is an address error too, and then a read returns 0 and reads nothing, and a write reaches the one register at the long's own address (`SH2_TIER` takes bits 7-0, the 16-bit `IPRB`, `VCRA`-`VCRD`, `ICR`, `IPRA` and `VCRWDT` bits 15-8 into their high byte) while the other registers under its four bytes are not written, said once; a word there reaches the register at the word's own address only, with the value's low byte, and the odd one beside it is neither written nor read; the low byte of `SH2_IPRB` and `SH2_VCRD` is reserved, and a byte write to it does nothing. The line shows the part (`VDP2_TVMD._1_1_ = 3;`); the note says what really happens. | Check the access width. Usually the code meant a whole-register access. |
| **0x…: a read of REG through the cached partition is a cache read when the cache is on** (amber) | A register read at a `0x0xxxxxxx` address (`0x05F80004` rather than `0x25F80004`). With the cache on (`SH2_CCR.CE`, which the games set) a hit returns the cached bytes without reading the hardware, so a poll of the register may never see it change, and a miss reads the whole 16-byte line, every register in it with its read effect. Writes are written through and get no caution. A pointer stepped in a loop whose later values read through the cached partition (`p = (p + 4) ^ 0x20000000`) gets the same caution on its read, whether or not a named register is near. The output cannot know whether the function runs with the cache off. | Read registers through `0x2xxxxxxx`; if the function runs with the cache off, ignore it. |
| **0x…: a misaligned N-byte read/write at … is an address error on the SH-2 … the access is made at …** (amber) | A word at an odd address or a long at a non-multiple of 4. Mednafen raises the error and makes the access at the aligned address, so the register that line prints is not the one reached; the caution names the one that is. On-chip the two halves differ: from `0xFFFFFF00` up the handlers align the address themselves (a word at `0xFFFFFF05` is the write to `SH2_DVDNT`, and divides), below it they decode the address as given (a word read at `0xFFFFFE11` is `SH2_FTCSR`, in bits 7-0, and arms its flags; it is not `SH2_TIER`). | Check the address. |
| **0x…: a 4-byte write at 0xFFFFFE20 is an address error … no register is named there** (amber) | A long access to an on-chip address below `0xFFFFFF00`, or a byte access at or above it, whether or not a register is there. | Check the width. |
| **if the pointer holds 0x… (REG): …** / **if the index is 0 (the pointer is based at 0x… (REG)): …** (amber or note) | The access is a plain load or store through a pointer, but the output names the registers it can hold: `puVar2 = &VDP2_TVSTAT; if (c) puVar2 = &VDP2_VCNT; … *puVar2`. Each is said as a direct access to it would be (the cache-read caution, the read effects, the width cautions, the write effects), one line for each register, prefixed with the pointer it applies to; "(it may hold other values too)" means a path of the pointer is not a constant. A pointer indexed from a register (`(&SCU_D0EN)[param_1 * 8]`) is said for the register itself, as "if the index is 0"; which register the index selects is not worked out. A pointer whose printed form names no register (a parameter, a loaded address, `param_1 - 1`) says nothing. A pointer moved between the cached and cache-through partitions with a mask (`(uint4)puVar1 & 0x1fffffff`, `| 0x20000000`) is followed through the mask, also when the loop applies it on one path only, applies two operations in a turn (`(p & 0xFFFFFFF0) ^ 4`) or an operation on one path and a step on the other: every value the loop can take under the masks is named. A pointer that is a number plus an unknown (`param_1 + 0x25F00000`) is taken to be based at the number when the number is a colour RAM or register address, and is said for the index 0. A pointer stepped in a loop (`puVar1 = puVar1 + 1`, or by an unknown amount) from a register, or from an address with a named register within 256 bytes, says "the pointer is stepped in a loop from 0x…: the iterations after the first reach other addresses, other registers perhaps, which are not said": the walk is not worked out (the trip count is not known, so how far it goes is not either; a callee's returned pointer is not followed at all). When the loop also masks the pointer into the cached partition, the note says the later iterations are cache reads too. | Read the line it prefixes. |

## Limits

- The output is pseudocode for reading, not source that compiles.
  Arithmetic on a value narrower than `int` is printed at the width the code does it (`(int4)-param_1` with a
  one-byte `param_1` negates a byte), where C would widen it first; and a widening cast such as `(uint8)x` of a
  signed `x` means a zero extension. Read the types, not C's promotion rules.
- Whether r0 is shown as the return follows the engine's rule, and not the instruction in `rts`'s delay slot. A value in r0 is the
  return when nothing else uses it (`mov #1,r0 ; rts`), or when it is the output of a call to a function whose signature is lent as
  returning a value (`return g(p);`, with whatever else the value is used for: compared, stored through). A value with another use
  (`return ++*p;`, `if (x == 5) *p = v; return x;`) is taken for scratch, as r0 is in every compiled function that leaves it as it was:
  the text says `return;` and the signature is lent `void`, for a function that returns the value as well as for one that does not, and
  the code cannot say which. Withholding every such function would withhold two lent signatures in five, so none is. A caller that reads
  r0 after calling one is withheld, not lent a result.
- A write to SR, GBR or VBR (`ldc`) is shown as a call, `Write_SR(value)`, `Write_GBR(value)`, `Write_VBR(value)`, where the
  code makes it: the interrupt mask, the base of the GBR accesses and the vector table are the caller's business, and the
  register the value comes from stays a parameter. `rte` shows what it restores the same way: `Write_SR(stacked SR & 0x3f3)` and
  `Rte_PC(stacked PC)`, so a handler that changes the words it will return through keeps its stores, and the SR is the one after the
  delay slot (`rte ; sett` writes `stacked SR & 0x3f2 | 1`). An input that is a byte of a
  register the function reads (the four bytes `cmp/str` compares) is named with the byte, counted from the least significant:
  `in_r3` is the low byte, `in_r3_b3` the most significant, and `unaff_r8_b3` the same for a register the function keeps. A return in both r0 and r1 is shown as an 8-byte value (`CONCAT44(r0, r1)`,
  `(uint8)x`) even when r1 is only a scratch register the function left a value in: the code does not say which.
- The pseudocode describes the instructions of an ordinary run. It does not model what the CPU does when it cannot
  carry one out, and it does not say so:
  - *Address errors.* A word or longword access at an address that is not a multiple of its size (`mov.w`, `mov.l`,
    `mac.w`, `mac.l`, the `@(disp,..)` forms), or a jump to an odd address, raises an address error on the SH-2 and
    the access is not completed. The output prints the access at the address the code computes, as if it had been
    made. (Only for the hardware registers listed above does the panel say that an access of that width is an address
    error.)
  - *Illegal instruction and illegal slot instruction exceptions.* A word that is not an instruction, or a branch (or
    another instruction that changes PC) in a delay slot, raises one. The output never shows the exception: such a
    word is printed as the instruction it would be, and an engine warning about the slot (not an exception) is as far
    as it goes.
  - *Interrupts.* They can run between any two instructions and are not shown. Neither is the one-instruction
    interrupt delay after `ldc`, `lds`, `stc` and `sts`.
  - *`sleep`.* It is shown as the call `Sleep_Standby()`; the output does not say that the CPU stops there until an
    interrupt or reset, or what Standby does to the on-chip modules.
  - *`tas.b`.* It is printed as a read of the byte, a test of it into T, and a write of it back with bit 7 set. On the SH-2 the pair is
    one bus-locked operation, and that is how the two CPUs of a Saturn take a lock from each other; the output does
    not show the locking, so nothing in it says that no other access can fall between the read and the write.
  None of this changes what a correct program computes. Where the code depends on one of these (an exception handler, a
  lock, a wake-up from `sleep`), read the assembly beside the pseudocode.
- Function boundaries are found heuristically, from a known entry or backwards to the previous `rts` plus slot. The scan skips literal pools and `mova` jump tables, and steps past a function that ends in a tail jump. A known entry keeps an address after an `rts` when flow from the entry reaches it (an early return). What the finder cannot settle is shown as an amber line. Expect to correct some entries with **Set Function Start Here**.
- Indirect calls stay indirect unless you are halted on them (see above).
- Only one level of pointer type is recovered for signatures. Structures are not inferred.
